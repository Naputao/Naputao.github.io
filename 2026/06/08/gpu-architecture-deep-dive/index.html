GPU 架构详解：从 Warp、SM 与 Memory Hierarchy 到 Tensor Core 的执行路径

Naputao Lv1

 Architecture Deep Dive

把 GPU 当成吞吐机器，而不是“更多核心的 CPU”

很多关于 GPU 的介绍停留在“并行更多、算得更快”这类结论上，但真正决定现代 GPU 形态的，是它如何组织线程、如何调度 warp、如何布置片上资源，以及如何用 memory hierarchy 把带宽和延迟拆成可管理的问题。下面这篇文章按整芯片 → SM → 调度 → 访存 → Tensor Core 的顺序，一层层把它拆开。

这不是一篇 CUDA 入门，也不是“GPU 就是更多核心”的泛科普。本文把现代 GPU 当成一个真正的吞吐型处理器来拆开：从整芯片视角、SM 内部组织、warp 调度、访存层级，一直讲到 Tensor Core 为何会改变整条执行路径。

为什么 CPU 思路无法直接解释 GPU

先给结论：GPU 的关键不是把 ALU 数量简单堆高，而是把线程组织、资源复制和调度策略一起围绕“隐藏延迟、追求吞吐”设计出来。

CPU 的目标通常是把单线程做得尽可能快：它会投入大量晶体管在复杂控制逻辑、乱序执行、分支预测、大缓存和更低延迟的执行路径上。因为 CPU 面对的是操作系统、应用逻辑、分支密集代码和不可预测访问模式，它必须在“单条控制流也要跑得很好”这件事上付出成本。

GPU 走的是另一条路。它默认你有大量近似同构的工作项，可以把很多线程捆成更大的调度单位，然后在某个 warp 因为访存而等待时，立刻换到另一个已经 ready 的 warp。换句话说，CPU 更像是尽力缩短一条控制流的等待时间；GPU 更像是让等待永远被别的工作覆盖掉。

因此，理解 GPU 时最忌讳的误区就是把它想成“更多核心的 CPU”。更准确的理解是：它是一台把计算阵列、资源复制、线程批调度、片上 scratchpad 和高带宽显存系统拼在一起的吞吐机器。

从全芯片视角看 GPU

如果只盯着某个 SM 或某条指令，很容易丢掉全局视角。更好的起点是先看整颗芯片：前端负责接收 kernel 与指令流；中间是大量计算簇和 SM；下方是统一的 L2；最外层才是 HBM / GDDR 与 memory controller。这个分层直接决定了 GPU 为什么擅长吞吐，却也经常被带宽与访存模式锁死。

把前端、SM 集群、L2 与显存控制器放到同一张图里看。

高亮路径表示一次典型 kernel 的执行区域：前端把 block 分派给可用 SM 集群，cluster 内部执行与访存命中优先留在片上，而 miss 才会下探到 L2 和片外显存。
每个 cluster 不是“单核”，而是一片可并行调度多个 warp 的执行资源区。复制这些 cluster，才是 GPU 扩展吞吐的基本方式。
统一 L2 让不同 SM 之间可以共享更多数据与缓存命中机会，但它同时也会成为全芯片争用点。
片外显存带宽很大，但延迟依旧高。GPU 真正强的地方，是让大量 warp 在等待显存时彼此掩护，而不是让某个线程单独等待得更少。

这张图里最重要的认知是：SM 只是整机中的执行岛。现代 GPU 的性能不是某个 ALU 决定的，而是前端分派、SM 资源占用、L2 压力、显存带宽、访存模式共同作用的结果。

线程、warp、block 与 kernel 的硬件映射

软件里你写的是 kernel、grid、block、thread；硬件里真正调度的却不是单个 thread，而是 warp。以 NVIDIA 语境来说，一个 warp 通常由 32 个线程组成，它们共享同一条指令流，但可在数据上分化。block 则是更大的分配单元：它决定一组线程能否一起驻留在某个 SM 上，并消耗掉该 SM 的寄存器、shared memory 与最大并发槽位。

这也是为什么 block 大小不是随便填的。它既影响并行粒度，也影响资源切分。如果单个 block 占用太多寄存器或 shared memory，那么一个 SM 上能同时驻留的 block 数就会下降，随之下降的不是“线程总数”这么简单，而是可供调度器轮换隐藏延迟的 warp 池深度。

更进一步说，warp 是执行单位，block 是资源绑定单位，而 kernel 只是逻辑上的一整批任务。把这三层关系分清，后面的 occupancy、调度和 bank conflict 才不会听起来像彼此无关的术语。

SM 内部到底长什么样

SM 并不是一个大核心，它更像是一组围绕 warp issue 组织起来的小型并行执行系统：上面有 warp scheduler 与 dispatch 单元，中间挂着寄存器文件与多类执行资源，旁边连着 load/store 路径和 shared memory / L1，再往下才会走向更远的 L2 与显存。

动画示意 2：SM 内部结构拆解图

点击不同区域，高亮该组件在执行路径中的职责。

Warp Scheduler 从 ready warp 池里挑选下一批可 issue 的 warp
Register File 线程私有状态与中间值的最快存储层
FP32 / INT / SFU / Tensor 不同类型指令走向不同执行阵列
Shared Memory / L1 线程块协作与近距离数据复用的关键区域
调度器不是“算得快”的地方，而是“决定谁先算”的地方。GPU 把很多晶体管投给了并行发射与 warp 轮换，而不是 CPU 式的大规模乱序逻辑。
寄存器文件既是性能来源，也是 occupancy 上限的约束来源。一个线程用太多寄存器，常常比“单条指令更慢”更致命，因为它会压缩整个 SM 的驻留并发度。
现代 GPU 的执行资源不是同质的。普通标量/向量计算、地址计算、特殊函数和矩阵乘加，会走向不同阵列；这意味着瓶颈分析必须看具体指令类别，而不是只看“利用率”。
shared memory 的价值不只是“更快”，而是“更可控”。它让程序员能主动把热点数据留在片上，但也引入了 bank conflict、容量限制和同步开销。

从性能角度看，SM 内部最值得记住的不是“里面有什么模块”，而是这些模块都在争夺同一件事：让足够多的 warp 在适当时刻拿到适当资源。寄存器太多、shared memory 占用太大、访存 miss 太多，最终都会表现为调度器手里可用的 ready warp 不够。

GPU 如何靠调度隐藏延迟

CPU 遇到 cache miss 时，往往靠乱序和 speculation 尽量填补空隙；GPU 的经典做法则更直接：当前 warp 如果等数据，就把 issue 机会让给另一个已经 ready 的 warp。只要 SM 上驻留的 warp 够多，这种切换看起来就像“延迟消失了”。

灰色表示等待数据返回，蓝色高亮表示当前 issue。只要 ready warp 足够多，SM 就能继续推进其他工作。

这就是为什么 occupancy 经常被拿来讨论，但又不能神化。occupancy 的本质是“在资源约束下，SM 最多能同时驻留多少 warp / block”。它重要，是因为更深的 warp 池更有机会覆盖访存等待；但它不是最终目的。如果你的 kernel 已经被计算阵列或某个特殊资源吃满，再继续追高 occupancy 并不会自动变快。

更准确的说法应该是：你需要足够的 occupancy 去支撑 latency hiding，但不需要为了数字好看而牺牲别的关键优化。很多实战里，合理的寄存器使用和更好的访存模式，比盲目把 occupancy 从 50% 堆到 100% 更有效。

Memory Hierarchy：真正限制性能的地方

如果说 SM 解释了 GPU 怎么发射和执行，那么 memory hierarchy 才解释了 GPU 为什么常常跑不满。现代 GPU 的算力往往大得惊人，但寄存器、shared memory、L1、L2、HBM/GDDR 之间的延迟与带宽差异更惊人。你以为自己在写“乘加”，硬件实际上可能在花大部分时间等数据。

看同一份数据从片外进入片上，再进入寄存器的层层收敛过程。

Registers线程私有，延迟最低，容量最小

L1 / Read-only Cache更接近执行单元的自动缓存层

Coalesced

相邻线程访问相邻地址，控制器能把请求合并成更少、更宽的事务。

Scattered

线程访问离散地址，事务被拆散，L2 与 memory controller 压力骤增。

理解这张图时，最重要的性能直觉有三个。第一，寄存器和 shared memory 的价值不只是快，而是它们能把数据留在离执行单元最近的地方。第二，L2 很重要，但它不是魔法缓存；坏的访问模式会让它很快变成拥堵点。第三，片外带宽虽然很宽，但任何一次真正掉到 HBM/GDDR 的 miss，都意味着你需要靠更多 ready warp 才能把空档填平。

因此，“coalescing”“bank conflict”“reuse”“tile”这些词并不只是 CUDA 教程里的技巧，它们背后对应的其实就是这张层级图里不同层之间的流量控制问题。

Tensor Core 为什么改变了 GPU 的形态

现代 GPU 已经不再只是“更大的通用并行阵列”。在 AI 工作负载主导之后，矩阵乘加成了最值得专门为之修建快车道的计算模式。Tensor Core 的意义不只是让某类运算更快，而是让 GPU 的执行资源开始明显分化：一部分继续服务通用 SIMT，一部分则直接针对矩阵 tile 计算做了专用设计。

一旦看到这一层，你就会理解为什么现代 GPU 文档越来越强调 mixed precision、tile size、tensor layout 和数据对齐。因为这类专用单元的收益取决于数据能否以它喜欢的形状和节奏被喂进去。也就是说，AI 时代的 GPU 架构演化，不只是“多加了一种指令”，而是把整个片上数据组织方式都往矩阵吞吐优化方向推了一步。

一个 warp 的完整执行旅程

前面的章节已经把零件拆开了。现在把它们重新串起来：一次 kernel launch 之后，前端先把 block 分配给有足够资源的 SM；SM 内部把线程组织成 warp；scheduler 从 ready warp 池里发出下一批指令；执行单元推进算术或地址计算；访存指令命中时快速返回，miss 时该 warp 被暂时挂起；期间其他 warp 获得发射机会；最终，当依赖消失，这个 warp 再次回到 ready 状态继续执行，直到 retire。

如果把 GPU 想成一条连续流水线，最容易误解它。更贴近真实的图景是：它在很多 warp 之间交错推进，每一步都可能因为资源、依赖或访存而暂停与切换。

这条“旅程图”最重要的价值，是把前面所有术语从静态名词变回动态过程。warp、scheduler、register、shared memory、L2、HBM、Tensor Core，这些词不是平铺在 PPT 上的标签，而是在同一条执行生命线上轮流成为瓶颈或加速器。

哪些概念是通用 GPU 原理，哪些是 NVIDIA 术语

本文主线用了很多 NVIDIA 术语，是因为它们最常见，也最容易形成完整叙述。但把这些词直接等同于“GPU 的唯一正确说法”会带来另一种误解。更好的做法是把它们分成两层：一层是通用架构原理，一层是厂商自己的命名。

NVIDIA 术语通用理解其他语境近似说法
Warp基本 SIMD/SIMT 调度束AMD Wavefront
SM流式多处理器 / 计算簇AMD CU
Shared Memory片上软件可控 scratchpadLDS
Tensor Core专用矩阵乘加单元Matrix Core / Matrix Engine

所以，真正值得记住的不是术语本身，而是它背后的约束：调度是不是按束进行、片上是否有显式 scratchpad、矩阵运算是否有专用单元、缓存层次和片外显存之间如何分工。这些问题才具有跨厂商可迁移性。

理解架构后应如何看性能问题

理解 GPU 架构之后，看性能问题最好按四种受限模式来排查。第一种是计算受限：执行阵列已经很忙，瓶颈在算术吞吐。第二种是带宽受限：L2 或片外流量已经吃满。第三种是延迟受限：理论带宽没满，但 ready warp 不够，等待无法被完全覆盖。第四种是资源受限：寄存器、shared memory 或 block 尺寸把驻留并发度卡死了。

很多优化建议其实都可以落回这四类里。调小寄存器压力，是在放宽资源受限；改成 coalesced 访问，是在缓解带宽与延迟受限；使用 shared memory tile，是在把数据从更高延迟层下拉到片上；正确喂给 Tensor Core，是在减少通用执行路径上的浪费。

最后一句总结：GPU 真正的强大，不在于“核心多”，而在于它把计算阵列、warp 调度、片上资源和 memory hierarchy 组织成了一台能够持续吞吐海量工作项的机器。看懂这件事，才算真正开始理解 GPU。
