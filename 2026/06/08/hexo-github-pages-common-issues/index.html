Hexo + GitHub Pages 常见问题排查：从部署到更新
Naputao Lv1
  2026-06-08 12:10:00 2026-06-08 12:10   2026-06-08 12:10:00  1088 Words  4 Mins  

仓库里原本已经有一篇完整的 Hexo 部署到 GitHub Pages 图文教程，这里不再重复基础步骤，而是把它整理成一份更适合出问题时快速定位的排查清单。

先把正确流程记清楚

正常流程其实只有四步：安装 Node.js / Git → 初始化 Hexo 项目 → 配置 deploy → 执行 hexo clean && hexo deploy。如果网页没更新，通常并不是“Hexo 不行”，而是某一个环节的状态与你想象的不一致。

最常见的 5 类问题

1. 仓库名不对

GitHub Pages 的用户主页仓库通常要求命名为 用户名.github.io。如果仓库名不符合规则，部署本身可能成功，但最终访问路径会与你预期不一致。

2. deploy 配置没有改完整

最容易漏的是 repo 和 branch。尤其是 branch 没写对时，你可能把内容推到了一个没有被 Pages 使用的分支。

3. 没安装部署插件

如果没有安装 hexo-deployer-git，执行 deploy 时往往会失败，或者提示找不到部署器。这种问题要先检查依赖，而不是重复点网页刷新。

4. 实际更新了，但浏览器缓存还在

这类情况最迷惑：你明明已经推送成功，仓库里也能看到新提交，但网站还是旧样子。处理方法很直接：强制刷新、开无痕窗口、等几分钟再访问。

5. 你改的是源文件，没重新生成静态页

如果只修改文章或主题文件，却没执行重新生成，最终推送到 Pages 的仍可能是旧内容。对于 Hexo 来说，“写完 → 生成 → 部署”是完整动作链。

一份可直接照抄的检查清单

  1. 确认仓库名是否正确。
  2. 确认 _config.yml 中 deploy 的 repo 与 branch 无误。
  3. 确认已安装 hexo-deployer-git。
  4. 重新执行 hexo clean、hexo deploy。
  5. 到 GitHub 仓库中看最新提交是否真的出现。
  6. 再去访问 用户名.github.io，必要时强刷或等待缓存刷新。

推荐思路：不要一上来就改配置。先判断问题属于“没有生成”“没有推送”“没有发布”还是“发布了但缓存没刷新”，再对症下手。

为什么要单独做这页

原始部署文章非常适合第一次跟着做，但当你第二次、第三次遇到问题时，更需要的是一份排错顺序。这也是把“教程”整理成“资料页”的价值：读者不是从零开始，而是在出错时快速回到正确轨道。
